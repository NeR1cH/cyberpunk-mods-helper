## 3. Архитектура

### 3.1. Что программа делает

Локальный помощник: сканирует папку Downloads и папку загрузок Vortex, находит точные копии (SHA-256) и старые версии архивов модов, строит HTML-дашборд, по подтверждению переносит лишнее в карантин. Модов не устанавливает. В папку игры и данные Vortex только читает.

Поток данных одного запуска `scan`:

```
scan_folder → extract_mod_meta (имя → название, Mod ID, версия)
  → mark_exact_duplicates (SHA-256 для файлов одинакового размера, через кэш хешей)
  → mark_versions → build_rows (группы = строки отчёта)
  → run_ai (названия через OpenRouter, кэш ai_cache.json)
  → анализ страниц Nexus (кэши nexus_*_cache.json)
  → render_dashboard → mod_audit_dashboard.html
server.py отдаёт страницу и обслуживает кнопки; clean (CLI или сервер) переносит файлы в карантин.
```

### 3.3. Сервер и страница

- `server.make_handler(downloads, dashboard, blacklist, config, port, quarantine, reveal_roots)` возвращает класс обработчика. Все настройки — аргументами, глобального состояния нет; так он и тестируется.
- Порядок проверок `do_POST`: `Host` → `Origin` либо `Sec-Fetch-Site: same-origin` → `Content-Type: application/json` → токен `X-ModAudit-Token` → размер тела ≤ 1 МБ → маршрут. Новый POST-эндпоинт, добавленный внутрь `do_POST`, получает всю защиту автоматически.
- Токен создаётся при запуске сервера и вписывается в `<meta name="api-token">` **при отдаче страницы** (`insert_token`); файл отчёта на диске не меняется.
- API: `/api/reveal`, `/api/blacklist`, `/api/clean/preview`, `/api/clean/apply`; `/api/delete` отвечает `410`.
- Очистка: `preview` возвращает `confirm` (HMAC по списку); `apply` без него или с другим списком отвечает `409 preview_required`, заново проверяет каждый файл и переносит только в карантин.
- Страница: данные лежат в двух JSON-блоках — `modAuditData` (массив файлов) и `modAuditMeta` (сейчас только `builtin_blacklist`). Выбор файлов — `Set` по `data-fid`, а `data-fid` — это индекс записи в `modAuditData`.
- Чистые функции JS собраны между метками `// <pure-logic>` и `// </pure-logic>`: `fmtSize`, `baseName`, `pickSelected`, `buildSelection`, `serverMessage`. Их исполняет `tests/test_dashboard_js.py` под Node.js. В этом блоке нельзя обращаться к DOM.

- **После каждой задачи — отчёт Никите:** файлы; что и почему; побочные эффекты; какие команды запускал и что вышло на самом деле; что проверить не удалось.
- **Проверки ставь перед коммитом жёстко:** `set -e` или цепочка через `&&`. Один коммит в прошлой сессии ушёл с хвостовым пробелом, потому что проверка стояла через `;`.
- **`docs/HANDOFF.md` обновляй в том же PR.**

- Крупные изменения (R01, D01, U01) сопровождай кратким описанием диффа и рисков: Никита отдаёт их на ревью второму ИИ.

### 5.2. Тесты не должны трогать файлы пользователя

Константы путей ядра указывают на папку проекта, где у Никиты лежат настоящие файлы. Что подменять:

| Что вызываешь в тесте | Что подменять |

### 5.3. Проверка дашборда в браузере

Работа с DOM тестами репозитория не покрыта. В прошлых сессиях она проверялась скриптами Playwright вне репозитория (не сохранены). Схема: скрипт на Python создаёт во временной папке архивы, вызывает `_scan_archive_roots` → `_prepare_scan_archives` → `build_rows` → `render_dashboard`, пишет HTML и поднимает `make_handler(..., port=<порт>)`; Playwright открывает страницу с `reducedMotion: 'reduce'` (иначе мешает заставка). Порт в `make_handler` обязан совпадать с портом сервера, иначе запросы получают `403 forbidden_origin`. Так проверялись: выбор галочками, предпросмотр и перенос в карантин, подписи дисков, кнопка чёрного списка.

Запуск: `python tools/r01_split.py report` показывает ссылки «вверх» по слоям (их нет, кроме одной разрешённой), `python tools/r01_split.py write` пишет восемь модулей и превращает `nexus_links.py` в фасад с реэкспортом. После записи выполни `ruff check modaudit nexus_links.py --select F401,F811 --fix` — скрипт копирует весь блок импортов в каждый модуль, лишние убирает ruff. Это локальный инструмент; в CI автоисправлений нет.

Проверено пробным прогоном: модули получаются чистыми для ruff и импортируются, сервер тоже. Что скрипт уже учитывает:

- Слои `config → names → scan → analysis → ai → render → clean → cli`; импорт только вниз.
- `MAX_MOD_ID` в других модулях читается как `config.MAX_MOD_ID`: значение меняется во время работы, копия через `from … import` устарела бы.
- Единственная ссылка вверх — `load_settings` → `find_cyberpunk_install` — закрыта импортом внутри функции.
- Аннотации в кавычках (`"Settings"`) считаются использованием имени.

**Что осталось сделать руками — перевод тестов.** После `write` падает 58 тестов из 212, и причина одна: тесты подменяют имена как `patch("nexus_links.ИМЯ")`, а после переноса функция ищет имя в своём новом модуле, и подмена фасада на неё не действует. Рекомендуемый путь:

1. Добавь `tests/support.py` с функцией `patch_core("ИМЯ", …)`, которая ставит **один и тот же** объект во все модули `modaudit`, где это имя привязано (один `MagicMock` на все, иначе разойдутся счётчики вызовов). Нужны `__enter__`/`__exit__` и `start`/`stop` — в тестах встречаются оба способа.
2. Замени в тестах `patch("nexus_links.ИМЯ", …)` и `patch.object(nexus_links, "ИМЯ", …)` на `patch_core("ИМЯ", …)`. Цели вида `nexus_links.shutil.move`, `nexus_links.webbrowser.open` — это объекты стандартной библиотеки, им хватит `patch("shutil.move")`.
3. Прямые обращения `nexus_links.ИМЯ` замени на `modaudit.<модуль>.ИМЯ`. Таблицу «имя → модуль» скрипт сохраняет в `tools/r01_where.json` (в Git её не добавляй). Особо: чтение `nexus_links.MAX_MOD_ID` в тестах обязано стать `modaudit.config.MAX_MOD_ID`, иначе читается устаревшая копия.
4. `Path(nexus_links.__file__).resolve().parent` → `modaudit.PROJECT_DIR`.
5. Тесты, читающие исходники как текст, переведи на новые файлы: `tests/test_config.py` (поиск `35000`, литерала порядка статусов, `os.environ.get("OPENROUTER_API_KEY"`), `tests/test_version.py` (владелец версии станет `config.py`), `tests/test_json_files.py`.
6. В `server.py` замени `nexus_links.ИМЯ` на импорты из модулей пакета и дай `_apply_clean_plan` публичное имя.

### 6.3. Этап 2 — идентификация через Nexus

## 8. Что не проверено

На настоящей Windows запускались только тесты в CI. Руками стоит проверить:

- `start.bat` целиком, включая ветку «нет `python`, есть `py -3`».
- Кнопку «В папке»: `explorer /select,"путь"` на пути с пробелами и кириллицей.
- Перенос в карантин между разными дисками и при занятом файле.
- Карточку Equipment-EX на своей установке.
- Доступность моделей по умолчанию (`nvidia/nemotron-3.5-lightning:free`, `google/gemma-4-31b-it:free`).
- Имя правообладателя и год в `LICENSE`.

Известные ограничения, оставленные как есть:

- Отчёты, созданные до S02/S06, с новым сервером не работают — их надо пересоздать.
- Очистка из дашборда — примерно до 2 000 файлов за раз (лимит тела 1 МБ).
- SHA-256 точных копий считается и в предпросмотре, и при применении.
- Карантин, подключённый внутрь Downloads как junction на другой диск, из скана не исключается.
- `.corrupt`-файлы кэшей не удаляются автоматически.
- Действия GitHub `actions/checkout@v4` и `actions/setup-python@v5` рассчитаны на устаревший Node.js 20 — обновить версии при случае.
- Общей защиты от тестов, читающих файлы пользователя, нет — только таблица из раздела 5.2.
